Notes on Slide 5

Slide 5 was the **"Anatomy of a Verifiable Credential"** slide — the dark-themed code slide showing a JSON-LD structure with color-coded annotations on the right. Here's a walkthrough of each section:

**`@context`** — This is the semantic layer. It tells any system reading the credential what the field names *mean*. Without it, "degree" could mean anything. By pointing to `https://www.w3.org/ns/credentials/v2`, you're saying "use the W3C vocabulary to interpret this document." You can stack additional context URLs for domain-specific terms.

**`type`** — Every VC has at least `"VerifiableCredential"` in this array, plus one or more domain-specific types like `"UniversityDegreeCredential"`. The type tells the verifier what kind of credential this is and what claims to expect inside it.

**`issuer`** — The entity that created and signed the credential. It's a DID (Decentralized Identifier) like `did:example:university`, not just a name string. This matters because a verifier can resolve that DID to a public key document and use it to verify the signature — no central database needed.

**`validFrom` / `validUntil`** — The credential's validity window, in ISO 8601 format. A verifier always checks the current time against these bounds. This is how credentials expire without needing to be explicitly revoked.

**`credentialSubject`** — The heart of the credential. This is where the actual claims live — *who* the credential is about (their DID, under `id`) and *what* is being asserted about them (their degree, license, age, etc.). This entire block can be selectively disclosed in a Verifiable Presentation.

**`proof`** — The cryptographic signature block. It records the algorithm used (`EdDSA`), which key signed it (`verificationMethod`), when it was signed, and the signature itself (`proofValue`). If anyone tampers with any field in the VC after signing, the proof becomes invalid — that's what "tamper-evident" means in practice.

The key insight is that these six sections aren't arbitrary — each one solves a specific trust problem: context solves ambiguity, issuer solves attribution, validity solves freshness, credentialSubject carries the claims, and proof makes it all unforgeable.



Notes on Slide 8

Slide 8 was the **"Key Technologies"** slide — a 2×2 grid covering the four technical pillars that make the VC ecosystem work. Here's a deep dive into each:

---

**1. Decentralized Identifiers (DIDs)**

A DID is a globally unique identifier that looks like `did:web:university.edu` or `did:key:z6Mkf5...`. The crucial difference from a URL or email address is that no central authority controls it — the holder owns it. Each DID resolves to a **DID Document** (you can see these in the prototype's Inspect tab) which contains the subject's public keys and service endpoints. This is what allows a verifier to look up an issuer's public key without calling a central registry — they just resolve the DID.

The `method` part (`:web:`, `:key:`, `:ion:`, `:ethr:`) determines *how* the DID is resolved — via a website, a blockchain, or a peer-to-peer network.

---

**2. Cryptographic Proofs**

Three main options appear in real deployments:

- **Ed25519** — An elliptic-curve signature scheme. Fast, compact, and the most common choice today. When an issuer signs a VC, they run the entire document through Ed25519 with their private key. Anyone with the public key can verify it, but nobody can forge it without the private key.
- **BBS+ Signatures** — The more powerful option. Unlike Ed25519 which signs the whole document as one blob, BBS+ signs *each claim individually* within a single signature. This is what enables true selective disclosure in a VP — the holder can reveal a subset of claims and still produce a valid cryptographic proof, without the verifier seeing the rest.
- **JWT (JSON Web Token)** — A widely-supported encoding format. Many existing systems already speak JWT, so VCs can be encoded as JWTs to ease adoption. The trade-off is less flexibility compared to the full JSON-LD proof model.

---

**3. Zero-Knowledge Proofs (ZKPs)**

This is the most sophisticated piece. A ZKP lets you prove a *statement* about your data without revealing the data itself. Classic example: instead of showing your date of birth to prove you're over 21, you present a ZKP that mathematically proves "the value in this field, when compared to today's date, yields an age ≥ 21" — and the verifier learns nothing else.

In the VC world, BBS+ signatures are the practical vehicle for ZKPs. The holder derives a proof from the original BBS+ signature that covers only the selected claims, and the verifier can confirm it's valid without ever seeing the hidden claims. This is a significant privacy leap over traditional credential systems where you typically hand over the whole document.

---

**4. Status & Revocation**

Credentials need to be revocable — a medical license can be suspended, a diploma can be rescinded. The challenge is doing this without the issuer tracking *who* is presenting *which* credential (which would be a privacy leak).

The **BitstringStatusList** (formerly StatusList2021) solves this elegantly: the issuer publishes a large bitstring where each bit position corresponds to one issued credential. A `0` means active, a `1` means revoked. The credential itself contains a pointer to its position in that list. When a verifier checks revocation, they download the bitstring and check one bit — they learn nothing about other credentials, and the issuer doesn't learn that a verification is happening.

---

The key thread connecting all four technologies is **decentralization and privacy** — each one is designed so that issuers, holders, and verifiers can interact without a central broker watching every transaction.
